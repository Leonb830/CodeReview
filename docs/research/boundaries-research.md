# OpenExecutive boundaries and adaptation notes

Inspected commit: `a59b4420291945c839d6d5be9c724568772d8b7c` (main, read 2026-10-23). Source inspection only; no application, tests, or live-model evaluations run.

## Code-verified reusable patterns

1. **Deterministic action gates around model-selected tools.** Department authority supports `auto_execute`, `propose_only`, and `escalate`. Held actions become server-side decisions preserving the exact call; handler wrappers check policy before running the inner handler and fail closed if lookup fails. This is a useful boundary between proposing a review and publishing it. The department policy itself is specific to this executive product and does not gate every principal/unattended flow. Sources: [department gate semantics](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/orchestrator/department_gate.py#L1-L27), [actual wrappers](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/orchestrator/department_gate.py#L378-L445).

2. **Persistent workflow state plus fenced ownership.** SQLite `workflow_runs` stores inputs/artifact/status, human-wait state, resume payload, attempts and fencing token. An atomic guarded update claims a resolved run; terminal writes require the current token, and heartbeats protect active resumptions. This is a useful design for review jobs surviving worker loss. It does not mean every ordinary chat turn is durably resumable. Sources: [schema](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/workflows/persistence.py#L58-L107), [claim](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/workflows/persistence.py#L511-L544), [heartbeat and fenced completion](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/workflows/persistence.py#L547-L617).

3. **Explicit approval records and partial-failure awareness.** `alert_approvals` records approver, edited content, status, session and outcome. `BEGIN IMMEDIATE` makes duplicate clicks/approvers converge on one running approval. Restarted approvals are marked failed with a warning that part of the action may already have happened. Sources: [approval claim](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/alerts/approvals.py#L89-L132), [partial-effects warning](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/alerts/approvals.py#L37-L42), [restart handling](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/alerts/approvals.py#L201-L211).

4. **Duplicate events and duplicate situations are distinct.** The alert pipeline suppresses repeats by `(source, external_id)`; a producer-supplied `dedup_hint` takes precedence over the model's key. Open alerts can be coalesced by source/key, updating their occurrence count/body and raising severity. Separate superseding support retains a link to the survivor. Sources: [pipeline](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/alerts/pipeline.py#L239-L274), [coalescing transaction](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/alerts/store.py#L389-L435), [superseding](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/alerts/store.py#L591-L622). These are useful patterns; they are not already PR finding identity or line-remapping logic.

5. **Bounded execution boundary.** Python file-processing jobs use Pyodide inside Deno. The actual subprocess grants reads only to the sandbox directory and worker script, omits network/write/process permissions, supplies a minimal environment, applies memory limits, caps output and kills over-time jobs. Sources: [purpose and limits](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/workflows/python_job.py#L1-L40), [subprocess and timeout](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/workflows/python_job.py#L422-L488). This is a data-processing sandbox with bundled libraries, not a general repository build/test runner.

6. **Structured observability and scenario evaluations.** Audit rows support session/turn/actor and structured details; full inputs/results are separate drill-down payloads. Audit errors are deliberately non-blocking. Eval scenarios run with bounded concurrency, optional cancellation, isolated per-session context, model-judge scores, and observed specialist routing checks. Sources: [audit design](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/audit/logger.py#L1-L24), [payload fields](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/audit/logger.py#L385-L413), [write failure](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/audit/logger.py#L487-L489), [eval runner](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/evals/runner.py#L1-L45), [score plus routing gate](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/evals/runner.py#L529-L559).

## Material limitations for a Code Review Agent

- **Single scheduler process.** The scheduler's source explicitly says its startup orphan-requeue sweep assumes one scheduler against the SQLite database. It is not ready-made horizontally scalable review infrastructure. Source: [scheduler contract](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/scheduler/runner.py#L1-L7), [startup requeue](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/scheduler/runner.py#L265-L275).
- **Durability is not exactly-once publishing.** Fenced state writes and atomic approval claims are valuable, but an external comment could succeed before the local completion write. A review publisher needs an outbox/reconciliation or another explicit idempotency strategy; the project's own partial-effects warning illustrates why.
- **Product identity is different.** The inspected integrations directory covers chat, mail, and workspace services, not a dedicated PR review adapter. GitHub Actions files review OpenExecutive's own contributions; they are not the backend's PR-ingestion implementation. The [fork review workflow](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/.github/workflows/claude-code-review-fork.yml) is nevertheless useful reference: maintainer label triggers, base-branch checkout, head-SHA checks before/after diff collection, restricted model tools, and a separate summary-posting step. It does not demonstrate a final head check immediately before every inline publication. Code review requires explicit repository/installation/PR/base SHA/head SHA identity, diff collection, reliable line anchors, and stale-head handling. These are proposed additions, not observed product features.
- **General quality judging does not prove findings.** Reuse the separation between generation and judgment, but evaluate reviews against labeled buggy and clean patches; verify file/line/commit evidence and reproducible failure where feasible. Do not use executive prose quality or confidence alone as a merge-blocking criterion.
- **Existing policy code is domain-specific.** MCP gateway checks Google/Microsoft senders, recipients, file access and private-mail boundaries. For reviews, use narrow read/review-publish capabilities bound to the repository and run; keep source content from authorizing privileged tool calls. Source: [gateway boundary](https://github.com/SenteLabsAI/OpenExecutive/blob/a59b4420291945c839d6d5be9c724568772d8b7c/packages/core/openexecutive/orchestrator/mcp_gateway.py#L3759-L3917).

## Recommended adaptation, pending interview decisions

Build a dedicated review pipeline around selected OpenExecutive patterns:

`PR event → durable job pinned to base/head → context collection → selected specialist passes → evidence verification + deduplication → review policy → idempotent publisher`.

Make read-only analysis and publication distinct permissions. Keep findings as structured records with evidence and scope before rendering prose. Supersede work when the PR head changes. If running repository tests is in scope, add disposable execution workers designed for the target languages; do not assume the existing Python document sandbox can do this.

Decisions the interview should resolve before implementation: review surface/trigger (PR, CLI, IDE), initial defect classes and languages, intended reviewer and success metric, operating model (one team vs hosted tenants), publication authority, and whether executing untrusted repository code is required.
