# Maintainability review policy research

Scope: source material for a new Code Review Agent. The skills were read as policy inputs; their review workflows were not executed. User priorities: overloaded files, long/complex functions, simpler alternatives, established libraries versus custom code, and comments explaining non-obvious intent. Stack: Python, TypeScript, React, Prisma, Next.js; Java remains a possible addition. Fixes occur only on request in an isolated branch/worktree.

## Observations from the supplied skills

- The code-review skill separates **Standards** and **Spec**, reviewed in independent contexts. It requires the standards reviewer to cite the documented rule or quote the relevant hunk; it reports a missing spec as unavailable rather than inventing one. [code-review L6–11](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/code-review/SKILL.md#L6-L11), [L25–41](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/code-review/SKILL.md#L25-L41), [L62–74](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/code-review/SKILL.md#L62-L74)
- Its baseline smells are explicitly **heuristics**: repository standards override them, and checks already enforced by tooling should be skipped. These are not automatic violations. [code-review L34–56](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/code-review/SKILL.md#L34-L56)
- The design skill values behavior hidden behind a small interface and keeping related change in one place. It explicitly rejects measuring module depth as a ratio of lines of code. Thus a large file or long function is a useful inspection signal, not sufficient evidence of a maintainability defect. [codebase-design L8–28](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/SKILL.md#L8-L28), [L60–65](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/SKILL.md#L60-L65), [L105–108](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/SKILL.md#L105-L108)
- Tests should exercise observable behavior through the interface and survive internal refactors; dependency strategies differ for in-process logic, local substitutes, owned remote services, and third-party services. [DEEPENING L5–37](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/DEEPENING.md#L5-L37)

## Seven candidate review criteria

The following is an inference from those sources plus the user's stated priorities, proposed for discussion. It is not a settled configuration.

| Criterion | Evidence needed to report it | Suppress the finding when |
|---|---|---|
| **1. File/module responsibilities are pulling apart.** Inspect large or frequently touched files for unrelated reasons to change. | Cite distinct responsibilities, their dependencies/callers, and a concrete change that unnecessarily touches both. Propose an extraction that reduces coupling or makes ownership clearer. | The file forms one cohesive implementation behind a simple interface, or splitting would scatter a single invariant. Line count alone is insufficient. |
| **2. A function hides several independently understandable operations.** Inspect long functions, nesting and repeated branching. | Identify the entangled decisions, state transitions or effects; show the maintenance/debugging burden; sketch a decomposition that preserves ordering, transactions, exception behavior and cleanup. | The function is a straightforward linear orchestration, parser/table, generated code, or a split adds many shallow helpers without making decisions easier to understand. |
| **3. One business rule is duplicated or scattered.** Look for duplicated knowledge, repeated type dispatch, shotgun surgery and divergent change. | Quote at least two locations implementing the same invariant and explain how a future rule change could diverge. Propose one owner or reusable operation at the right scope. | Similar syntax serves independent business concepts, lifecycle requirements differ, or abstraction would tie unrelated features together. |
| **4. An abstraction costs more than it hides.** Apply the deletion test to wrappers, factories, configuration hooks and speculative extension points. | Show the caller ceremony and what complexity actually disappears or spreads if the abstraction is removed. Cite real callers and actual variation before proposing a port or generic framework. | The abstraction centralizes meaningful policy, validation, compatibility, lifecycle or test substitution, even if its body is short. |
| **5. Interfaces and tests force callers to know implementation details.** Inspect data clumps, primitive domain values, message chains, hidden side effects and brittle internal mocks. | Cite repeated argument bundles, invalid combinations, ordering assumptions or tests coupled to internals. Explain a smaller contract/type or appropriate dependency seam and demonstrate a simpler caller/test. | The proposed type/adapter has no demonstrated consumer, actual variation or test need; its ceremony exceeds the behavior it protects. |
| **6. Custom machinery has a demonstrably simpler supported alternative.** Start with an existing project helper, standard library or framework capability before proposing a new package. | Identify exact behavior currently reimplemented; verify a candidate API in the installed/target version against primary docs; compare semantic edge cases, runtime compatibility, integration work and dependency cost. Show the net reduction, including adapter/glue code. | The candidate merely exists, differs in needed semantics, requires an unjustified dependency or upgrade, is incompatible with server/client/runtime constraints, or lacks evidence of suitability. |
| **7. Non-obvious intent is missing or misleading.** Look for surprising workarounds, unusual ordering, retry/transaction constraints, performance choices and suppressed checks. | Cite the exact surprising behavior and the invariant or external constraint a maintainer needs to preserve. Recommend a concise “why” comment near the decision, ideally with the relevant issue or source when available. | A better name or simpler structure removes the ambiguity; the behavior is self-explanatory; the comment would restate syntax; or intent cannot be established from evidence. Do not invent a reason. |

Source mapping: criteria 1–5 adapt the smell baseline and design principles; criterion 2 explicitly adds the user's long-function priority without imposing a numeric rule. Criteria 6–7 are extensions from the user's library and intent-comment priorities; neither supplied skill establishes a package-selection policy or mandates comments everywhere. [code-review L43–56](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/code-review/SKILL.md#L43-L56), [codebase-design L54–65](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/SKILL.md#L54-L65), [L67–95](https://github.com/lb830/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/codebase-design/SKILL.md#L67-L95)

## Candidate evidence gate

An actionable maintainability finding should state:

1. **Location and revision:** the reviewed commit, relevant changed lines and supporting callers or related code.
2. **Observation:** what the code actually does, distinguished from inferred future risk.
3. **Maintenance consequence:** the concrete knowledge duplication, coupling, reasoning burden or likely change failure—not “this is cleaner.”
4. **Smallest useful alternative:** enough detail to assess the suggestion without pretending a speculative rewrite has been tested.
5. **Tradeoff and counterevidence:** behavior to preserve, migration cost, repository convention or justified exception.
6. **Policy classification:** documented-standard violation, evidence-backed design suggestion, or unresolved question; state missing context.

This gate is a proposed synthesis, not a requirement quoted verbatim from either skill. Numeric LOC/complexity metrics should prioritize inspection unless the repository explicitly adopts a threshold. Existing lint, formatter and type-checker results should be consumed or linked without duplicating their comments. Distinguish a new issue from pre-existing debt encountered for context. Do not assert spec noncompliance when no authoritative spec is available.

## Still unsettled by this research

The sources do not establish the user's preferred report volume, tolerance for opinionated suggestions, when repository-wide debt belongs in a PR review, exact review lenses, severity terminology, Java scope, or allowed dependency recommendations. Those are product decisions for the interview. No implementation or automatic-fix action was taken.
